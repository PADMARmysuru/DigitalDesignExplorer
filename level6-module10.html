Verification Components

Module 9 showed the team. This module shows how to build each member and how they talk: transactions carry data, mailboxes pass them between threads, events and semaphores coordinate timing, and fork/join runs everything in parallel.

Learning objectives

By the end of this module you will be able to:

  1. Write a transaction class and explain what each component does with it.
  2. Assemble generator, driver, monitor, scoreboard, agent, environment and test in the right hierarchy.
  3. Use a mailbox with put, get, try_put, try_get and a bounded size.
  4. Synchronise threads with events and share resources with semaphores.
  5. Choose between fork ... join, join_any and join_none.

The components and their hierarchy

An agent groups everything for one interface (generator or sequencer, driver, monitor). The environment holds agents plus the scoreboard and coverage. The test builds and configures the environment.

class txn;                                  // the transaction: data only
  rand bit [7:0] a, b;
  bit      [8:0] sum;
  function string show(); return $sformatf("a=%0d b=%0d sum=%0d", a, b, sum); endfunction
endclass

class agent;
  generator gen;  driver drv;  monitor mon;
  mailbox #(txn) gen2drv = new();
  function new(virtual adder_if vif, mailbox #(txn) mon2sb);
    gen = new(gen2drv);  drv = new(vif, gen2drv);  mon = new(vif, mon2sb);
  endfunction
  task run(); fork gen.run(); drv.run(); mon.run(); join_none endtask
endclass

Mailboxes

A mailbox is a thread-safe queue between two processes. put and get block (wait) when the mailbox is full or empty; try_put and try_get never wait and return 0 if they could not do it. new(2) makes a bounded mailbox that holds at most 2 items.

Events and semaphores

An event is a signal between threads: one triggers it with ->, others wait with @ or wait(ev.triggered). A semaphore is a bucket of keys: a thread takes a key with get() before using a shared resource (such as a bus) and returns it with put().

event reset_done;
initial begin  apply_reset();  -> reset_done;  end       // trigger
initial begin  @(reset_done);  start_traffic();  end     // wait for the trigger

semaphore bus_key = new(1);                              // one key: one user at a time
task automatic use_bus(string who);
  bus_key.get(1);   drive_something(who);   bus_key.put(1);
endtask

fork ... join, join_any, join_none

fork starts several threads in parallel. The keyword at the end decides when the parent continues.

Practice questions

Work these on paper first, then open the model answer.

1. Why use a bounded mailbox between generator and driver?

An unbounded mailbox lets the generator create thousands of transactions at time 0 before the driver sends any. Bounding it (e.g. size 1) keeps the generator just one step ahead, saving memory and keeping log messages in a sensible order.

2. Write a timeout: run wait_for_done() but give up after 1000 ns.
fork
  wait_for_done();
  begin #1000ns; $error("timeout"); end
join_any
disable fork;
3. What is the difference between @(ev) and wait(ev.triggered)?

@(ev) waits for a future trigger; if the event was triggered earlier in the same time step, it is missed. wait(ev.triggered) also succeeds if the event has already been triggered in the current time step, avoiding that race.

4. Why does env.run() usually start its components with join_none?

Drivers, monitors and scoreboards contain forever loops and never finish. With join, run() would never return and the test could not decide when to stop.

5. Two monitors write to the same log file. How can you stop their lines from interleaving?

Guard the write with a semaphore of one key: log_key.get(); write lines; log_key.put();.
