SystemVerilog Assertions (SVA)

An assertion is a rule about your design that the simulator checks on every clock cycle. Instead of staring at waveforms hoping to spot a mistake, you write the rule once and the tool tells you exactly when and where it was broken.

Learning objectives

By the end of this module you will be able to:

  1. Explain why assertions find bugs earlier than output checking alone.
  2. Write immediate assertions in procedural code.
  3. Write clocked concurrent assertions with property and sequence.
  4. Tell |-> from |=> and use ##n and ##[m:n] delays.
  5. Use $past, $rose, $fell, $stable and $changed.
  6. Use disable iff to switch checks off during reset.
  7. Predict, from a waveform, whether an assertion passes or fails, and explain why.

Module 2 (clocked logic) and Module 6 (interfaces). Comfort reading waveforms helps.

Why assertions?

A scoreboard only notices a bug when a wrong value reaches an output, maybe thousands of cycles after the cause. An assertion sits right next to the logic and fires on the cycle the rule is broken, pointing at the exact signal.

Immediate assertionConcurrent assertion
WhereInside procedural code (always, initial, tasks)Module, interface or program level (also in procedural code)
When checkedWhen the statement executesAt every clock edge
Can span cyclesNoYes: sequences over many cycles
Exampleassert (addr < 16);assert property (@(posedge clk) req |=> ack);
// Immediate: a simple check at one moment
always_comb
  a_onehot: assert ($onehot0(state)) else $error("state %b is not one-hot", state);

// Concurrent: a rule over time, sampled at each rising clock edge
a_ack: assert property (@(posedge clk) disable iff (!rst_n)
                        req |-> ##[1:3] ack)
       else $error("ack did not arrive within 3 cycles of req");

A concurrent assertion samples every signal just before the clock edge (like a clocking block). In the waveforms below, each column is one clock edge and shows the value sampled there.

Sequences, properties and implication

A sequence describes signal values over consecutive clock cycles. A property combines sequences into a rule, usually an implication: if the antecedent happens, then the consequent must follow.

sequence s_req_ack;
  req ##1 ack;              // req, then ack one cycle later
endsequence

property p_handshake;
  @(posedge clk) disable iff (!rst_n)
    req |-> ##[1:3] ack;    // antecedent |-> consequent
endproperty

a_handshake: assert property (p_handshake);
c_handshake: cover  property (p_handshake);   // counts how often it really happened
OperatorMeaning
a |-> bOverlapping: if a at this edge, b must hold at the same edge
a |=> bNon-overlapping: if a at this edge, b must hold at the next edge (same as a |-> ##1 b)
##nWait exactly n clock cycles
##[m:n]Wait between m and n cycles: passes at the first cycle that matches
disable iff (c)Abandon the check while c is true (typically reset)

If the antecedent is false, the property is vacuously true: nothing is checked on that cycle. That is why a cover property is useful, to prove the antecedent actually happened.

Sampled value functions

These functions compare the value sampled at this clock edge with the value at the previous edge.

FunctionTrue when
$rose(a)a was 0 at the previous edge and is 1 now
$fell(a)a was 1 and is 0 now
$stable(a)a has the same value as at the previous edge
$changed(a)a has a different value (the opposite of $stable)
$past(a, n)Returns the value of a n edges ago (n = 1 by default)

Practice questions

Work these on paper first, then open the model answer.

1. Write an assertion: whenever start rises, done must be high within 2 to 5 cycles.
assert property (@(posedge clk) disable iff (!rst_n)
                 $rose(start) |-> ##[2:5] done);
2. What is the difference between req |-> ##1 ack and req |=> ack?

None: they are equivalent. |=> is shorthand for an overlapping implication followed by a one-cycle delay.

3. An assertion never fails, but the feature is broken. How can that happen?

The antecedent may never be true, so the assertion is vacuously true on every cycle. Add a cover property on the antecedent (or the whole property) to prove it actually triggered.

4. Write an assertion that count increases by exactly 1 on every cycle where en is high, except during reset.
assert property (@(posedge clk) disable iff (!rst_n)
                 en |=> count == $past(count) + 1);
5. Why use disable iff (!rst_n)?

During reset, signals are forced to reset values and many rules do not apply. Without disable iff, an assertion that started just before reset could fail spuriously. The check is abandoned whenever the condition is true.
