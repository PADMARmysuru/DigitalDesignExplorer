Testbench Architecture

A professional testbench is not one long initial block. It is a small team of components, each with one job: create stimulus, drive pins, watch pins, predict and compare. This module shows how the team is organised and how a transaction travels through it.

Learning objectives

By the end of this module you will be able to:

  1. Name the components of a layered testbench and describe each one's job.
  2. Follow a transaction from generator to scoreboard.
  3. Explain why a self-checking testbench with a reference model scales better than checking waveforms by eye.
  4. Compare directed and constrained-random testing, and say when each is useful.

Directed vs constrained-random testing

A directed test uses values you chose by hand; it proves the cases you thought of. A random test lets the solver pick values; it finds the cases you did not think of. Real projects use both: directed tests for reset and specific corner cases, random tests for volume.

DirectedConstrained random
Who picks the valuesYouThe solver, within your constraints
Finds unexpected bugsRarelyOften
Needs a self-checking scoreboardOptional (expected values can be hard-coded)Essential (you cannot hand-compute thousands of results)
Knowing what was testedObviousRequires functional coverage (Module 11)

Self-checking and reference models

A self-checking testbench decides PASS or FAIL by itself. The reference model (also called the predictor) computes what the DUT should produce; the scoreboard compares prediction with reality and counts errors.

class scoreboard;
  mailbox #(adder_txn) mon2sb;
  int n_ok, n_err;

  function bit [8:0] ref_model(bit [7:0] a, b);   // the predictor
    return a + b;
  endfunction

  task run();
    adder_txn t;
    forever begin
      mon2sb.get(t);                               // blocks until the monitor sends one
      if (t.sum === ref_model(t.a, t.b)) n_ok++;
      else begin
        n_err++;
        $error("a=%0d b=%0d: DUT sum=%0d, expected %0d", t.a, t.b, t.sum, ref_model(t.a, t.b));
      end
    end
  endtask

  function void report();
    if (n_err == 0) $display("TEST PASSED: %0d transactions", n_ok);
    else            $display("TEST FAILED: %0d errors", n_err);
  endfunction
endclass

Practice questions

Work these on paper first, then open the model answer.

1. Why does the monitor not simply get transactions from the generator?

The monitor must report what really happened on the pins, not what was intended. If the driver or the DUT corrupts or drops something, only an independent monitor sees it.

2. Where would you put a check that valid never goes X after reset?

In an assertion bound to the interface or DUT (Module 7). Protocol rules belong in assertions; data correctness belongs in the scoreboard.

3. The reference model and the DUT were written by the same person from the same misunderstanding. What happens?

Both are wrong in the same way, so the scoreboard sees no mismatch. This is why models are ideally written independently from the specification, and why reviews and assertions from the spec matter.

4. List the components that must know about the virtual interface.

Only the driver and the monitor (plus any component that waits on the clock). Generator, scoreboard and reference model work purely with transactions.

5. Why should a random test print its seed?

So a failure can be reproduced. Re-running with the same seed generates the same random sequence, letting you debug the exact failing case.
