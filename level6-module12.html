Verification Projects

Time to put everything together. Each project takes a small design through the complete verification flow: RTL, testbench, assertions, constrained randomization, functional coverage and a final PASS/FAIL verdict. Every project hides a realistic bug you can switch on to see which part of the testbench catches it.

Learning objectives

By the end of this module you will be able to:

  1. Read a complete verification environment for a small design and explain each part.
  2. Run a verification flow and interpret scoreboard results, assertion results and coverage together.
  3. Recognise which checker (scoreboard or assertion) catches which kind of bug.
  4. Decide when a design is ready for sign-off.

When is verification done?

No real project is ever "fully" verified; teams sign off when agreed goals are met.

  1. All directed and random regression tests pass, over many seeds.
  2. No assertion failures, and cover properties show every assertion was actually triggered.
  3. Functional coverage goals from the verification plan reach 100% (or every hole is reviewed and waived).
  4. Code coverage is reviewed: unreached code is either tested or explained.
  5. Every bug found is fixed, re-tested and has a test that would catch it again.

Practice questions

Work these on paper first, then open the model answer.

1. In the FIFO project, the scoreboard sometimes passes even with the bug on. Why, and what catches it every time?

If the random stimulus never tries to write a fourth entry, the early full flag never changes any data, so the scoreboard sees nothing wrong. The assertion full == (count == 4) checks the flag every cycle, so it catches the bug as soon as the FIFO holds three entries. Coverage shows whether the full case was reached.

2. The UART bug (MSB first) is not caught by the start/stop-bit assertions. Why?

Those assertions only check the frame's framing bits, which the bug does not touch. Only the scoreboard, which decodes the data bits and compares them with what was sent, sees the reversed byte.

3. Design a coverage bin that would have proved the FSM's overlapping case was tested.
cp_overlap: coverpoint (detect && $past(detect, 3)) { bins hit = {1}; }

Or a cover property: cover property (@(posedge clk) detect ##3 detect);

4. Why do the RAM project's writes and reads need to cover both halves of the address space?

The aliasing bug (address bit 3 ignored) only shows when an address in one half and its partner in the other half are both written, then read. Coverage of both halves and of address pairs makes sure this situation occurs.

5. Your ALU passes 1000 random tests with 100% coverage. Name one more thing to check before sign-off.

Run with several different seeds; review the coverage model against the specification (for example, flags such as carry or overflow may have no coverpoint); check that the reference model was written independently; and confirm there are no assertion failures or unexpected X values.
