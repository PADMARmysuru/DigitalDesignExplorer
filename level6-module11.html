Functional Coverage

Random tests raise an obvious question: what did they actually test? Functional coverage answers it. You list the situations that matter, and the simulator counts which of them really happened. Only when every item is covered are you done.

Learning objectives

By the end of this module you will be able to:

  1. Tell code coverage from functional coverage.
  2. Write a covergroup with coverpoints and explicit bins.
  3. Use ignore_bins and illegal_bins.
  4. Measure cross coverage between two coverpoints.
  5. Read a coverage report, find the holes and close them with constraints or directed tests.

Code coverage vs functional coverage

Code coverage is measured automatically from the RTL: which lines, branches, conditions and toggles were exercised. Functional coverage is written by you from the specification: which features, values and combinations were exercised. You need both: 100% code coverage can still miss an entire feature that was never implemented.

Code coverageFunctional coverage
SourceGenerated from the RTL by the toolWritten by the verification engineer
MeasuresLines, branches, conditions, toggles, FSM statesSpec features, value ranges, combinations, sequences

Covergroups, coverpoints and bins

A coverpoint watches one variable or expression. Bins split its values into buckets; a bin is covered once it has been hit at least once. A cross covers every combination of the bins of two coverpoints.

typedef enum logic [2:0] {ADD, SUB, AND, OR, NOP=3'b110, RSV=3'b111} op_t;

covergroup cg_alu @(posedge clk iff valid);
  cp_op: coverpoint op {
    bins        arith[] = {ADD, SUB};     // [] = one bin per value
    bins        logic_[] = {AND, OR};
    ignore_bins nop     = {NOP};          // not interesting: excluded from the score
    illegal_bins rsv    = {RSV};          // must never happen: reports an error if hit
  }
  cp_a: coverpoint a {
    bins zero  = {0};
    bins small = {[1:127]};
    bins large = {[128:254]};
    bins max   = {255};
  }
  cx_op_a: cross cp_op, cp_a;           // 4 ops x 4 ranges = 16 combinations
endgroup

cg_alu cov = new();                     // a covergroup must be constructed

Closing coverage

Coverage-driven verification is a loop: run random tests, read the coverage report, and for each hole either adjust constraints (so random reaches it) or write a directed test. Stop when the coverage goals are met and all tests pass.

Write coverage model
→
Run random tests
→
Analyse holes
→
Tune constraints / add directed tests
→
Repeat until 100%

Coverage says what was exercised, not whether the result was correct. A bin can be hit while the scoreboard reports an error. Sign-off needs both: all tests passing and coverage goals met.

Practice questions

Work these on paper first, then open the model answer.

1. Write a coverpoint for a 4-bit len with bins for 0, 1–7, 8–14 and 15.
cp_len: coverpoint len {
  bins zero = {0};
  bins low  = {[1:7]};
  bins high = {[8:14]};
  bins max  = {15};
}
2. How many cross bins does cross cp_x, cp_y have if cp_x has 3 bins and cp_y has 5?

15: every combination of one bin from each coverpoint.

3. Random tests have run for hours but a == 255 is never covered. What do you do?

With uniform 8-bit values, 255 appears only 1 time in 256. Add a dist constraint giving corner values extra weight, or write a short directed test for that value.

4. What is the difference between ignore_bins and illegal_bins?

ignore_bins removes values from the coverage calculation quietly (not interesting). illegal_bins also removes them, but reports an error if they occur (must never happen).

5. Why can 100% functional coverage still leave bugs?

Coverage only records what was exercised. If the coverage model is incomplete (a feature has no coverpoint), or the checker is missing, bugs can remain. The coverage plan must be reviewed against the specification.
